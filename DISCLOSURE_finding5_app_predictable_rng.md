# Finding #5 — iCSee provisioning app uses a predictable PRNG for device credentials (CWE-338)

**Researcher:** Artyom Bordulev ([@Raizer1996](https://github.com/Raizer1996))
**Advisory:** XM210-2026-005 (new finding — new CVE request; does not amend CAN-2026-2037011/-2037013/-2037014)
**Component:** iCSee Android application `com.xm.csee`, version 7.9.5_G (versionCode 79531)
**Weakness:** CWE-338 — Use of Cryptographically Weak PRNG
**Method:** static analysis of the application package (decompilation); no device or network interaction
**Severity:** CVSS v3.1 `AV:A/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H` — Base **7.0 (High)**

## Summary

During Wi-Fi / AP provisioning, the iCSee application generates a new device administrator
account (username and password) and provisions it onto the camera. The values are produced by
`org.apache.commons.lang3.RandomStringUtils.randomAlphanumeric()`, which in the bundled library
version is backed by a single shared static `java.util.Random` — a 48-bit linear congruential
generator, not a cryptographically secure RNG. The generator's internal state is recoverable from a
small number of observed outputs, after which subsequent outputs are predictable. An adversary able
to recover that state can derive the administrator password set on the device.

## Affected logic

The provisioning path constructs a credential-change request containing app-generated values:

```
NewName = RandomStringUtils.randomAlphanumeric(8)    // 8-character alphanumeric username
NewPwd  = RandomStringUtils.randomAlphanumeric(16)   // 16-character alphanumeric password
```

Observed in the decompiled provisioning activities
(`com.xworld.activity.adddevice.QuickConfigResultActivity`, `SearchDevActivity`, and the
Bluetooth add-device activities).

## Root cause

Bundled `org.apache.commons.lang3.RandomStringUtils` (Apache-2.0; the security-relevant lines):

```java
import java.util.Random;
private static final Random RANDOM = new Random();          // java.util.Random — shared, static
public static String randomAlphanumeric(int n) { ... RANDOM ... nextInt ... }
```

- `java.util.Random` is a 48-bit LCG. There is no `SecureRandom` in the class.
- The 48-bit state is recoverable from approximately two consecutive 32-bit `nextInt()` outputs;
  thereafter all outputs are deterministic. The static instance is shared across every
  `RandomStringUtils` call in the app, enlarging the observation surface.
- The 8/16-character length does **not** mitigate this — predictability is a property of the RNG,
  not of the output length.

Apache Commons Lang added cryptographically secure variants
(`RandomStringUtils.secure()` / `secureStrong()`) in release 3.16.0; the bundled build predates or
omits them.

## Impact

An adversary who recovers the generator state can predict the administrator password the app sets
on the device and authenticate as administrator (full access to the device and its configuration).
`AC:H` reflects that the attacker must first observe at least one generator output; the most
plausible path is presence on the local network during provisioning, hence `AV:A`. A demonstrated
remote means of obtaining an output would raise the vector to `AV:N` (Base 8.1).

## Remediation

- Replace the insecure generator with a CSPRNG: `RandomStringUtils.secure()` (commons-lang3 ≥ 3.16)
  or a `java.security.SecureRandom`-backed generator. Do not reuse a shared `java.util.Random` for
  security-sensitive tokens.
- Treat the provisioned administrator password as a secret in transit.

## Relationship to Finding #4 (attribution correction)

Finding #4 (XM210-2026-004) is phrased as *"iCSee generates weak admin credentials — 4-character
`[a-z]` username + 6-character `[a-z0-9]` password."* Analysis shows this describes a **different,
device-side** credential set:

- The 4-character `[a-z]` / 6-character `[a-z0-9]` account is generated **on the device** and is
  **read** by the app via the DVRIP `GetRandomUserInfo` request — it is not generated by the app.
  Its weakness is **insufficient length** (~31 bits of entropy) → **CWE-521**, attributable to the
  device/firmware.
- The predictable-PRNG weakness in **this** advisory (Finding #5) is a **separate** issue in the
  **application's own** 8/16-character credential generation → **CWE-338**.

Recommended wording: **Finding #4 → device/firmware, CWE-521 (insufficient credential length)**;
**Finding #5 → application, CWE-338 (predictable PRNG)**. Two distinct root causes in two distinct
components. (The device-side generator's RNG primitive itself was not assessed within this
report's observational, APK-static scope.)

## Reproducibility

- Application: `com.xm.csee` 7.9.5_G, SHA-256 `cf79fbfe176b6013240b5d15c629a84ca4d985291044ec8bbddef9940d8602e9`.
- The `RandomStringUtils` code path and the `ChangeRandomUser` provisioning flow are reproducible by
  decompiling the APK (e.g. with jadx) and inspecting the add-device activities.
